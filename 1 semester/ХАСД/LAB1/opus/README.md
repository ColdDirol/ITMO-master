# Практическая работа №1 — формат HCF

Бинарный формат для датасета `dataset.jsonl` (русскоязычные тексты, написанные человеком)
и кодер/декодер к нему на Java без внешних зависимостей.

**Результат: 529 735 512 → 80 657 358 байт, коэффициент 6.57x (1.218 бита на исходный байт).**
Декодированный файл побайтово совпадает с исходным (sha256 идентичны).
Кодирование 91 с, декодирование 2.4 с при бюджете 5 минут на гигабайт
(то есть 152 с на этот файл) — с запасом в 1.7 раза по кодированию и в 60 раз по декодированию.

```
исходный   dataset.jsonl          529 735 512 Б   sha256 8173e925a466738e…
кодировано dataset.hcf             80 657 358 Б   6.57x
декодировано dataset.decoded.jsonl 529 735 512 Б  sha256 8173e925a466738e…  ← совпадает
```

## 2. Устройство формата

```
[ HEADER ]
  "HCF1", версия
  число строк, размер группы
  ШАБЛОН СТРОКИ          — вся разметка JSON, один раз на файл (558 Б)
  ОПИСАНИЯ СТОЛБЦОВ      — выбранный кодек + его константы/словари (178 Б)
  СЛОВАРЬ ФРАЗ           — «внешние данные» текстового кодека (8 395 912 Б)
  ПОТОК ИСКЛЮЧЕНИЙ       — строки, не совпавшие с шаблоном (0 Б)
[ ГРУППЫ СТРОК по 4096 документов ]
  для каждой группы: для каждого столбца — длина блока + блок
[ 0 ]  — маркер конца
```

### 2.1 Шаблон строки: разметка бесплатно

Схема у всех строк одна, значит вся «разметка» — константа. Шаблон — это
последовательность сегментов: литерал (обязан совпасть байт в байт), слот значения
(уходит в столбец), повторяющаяся группа (массив `sentences`: подшаблон элемента,
литерал-разделитель и слот для длины массива).

Шаблон **выводится автоматически из первой строки файла** и затем проверяется на каждой
строке. Это даёт два свойства:

* 247 байт разметки на строку × 53 410 строк = 68.6 МБ (12.9 % файла) кодируются 558 байтами;
* строка, не совпавшая с шаблоном, уходит в поток исключений «как есть», поэтому
  побайтовая точность гарантирована для любых входных данных, а не только для этого файла
  (есть тест: строка с другим набором ключей в середине файла).

### 2.2 Столбцовые кодеки

Кодек выбирается автоматически по измеренной в первом проходе статистике и пишется
в заголовок — формат самоописываемый.

| кодек | когда выбирается | как работает |
|---|---|---|
| `ALLNULL` | все значения null | 0 бит данных |
| `CONST` | одно различное значение | значение в заголовке, 0 бит данных |
| `DICT` | < 4096 различных значений | словарь в заголовке + поток номеров |
| `IDNUM` | `префикс_цифры` | словарь префиксов + число + ширина поля (3 потока целых) |
| `DATE` | `YYYY-MM-DD` | номер дня от эпохи |
| `NUM` | целые | см. ниже |
| `TEXT` | остальное | словарь фраз, раздел 3 |

Целочисленные потоки (в том числе номера словаря, даты, длины значений) режутся на куски
по 1024 значения; для каждого куска кодер **измеряет** размер во всех режимах и выбирает
лучший, записывая номер режима в 3 бита:

* `CONST` — все значения куска равны;
* `FOR` — frame of reference: `v − min` в фиксированных `w` битах;
* `DELTA` — зигзаг-разности кодом bit-varint(k), `k` подбирается из {1,2,3,4,6,8};
* `RLE` — серии (значение, длина);
* `PFOR`, `PFOR_DELTA` — patched frame of reference: `w` бит на значение, код `2^w−1`
  зарезервирован как «исключение», после него идёт полный varint. Это позволяет держать
  узкое поле при редких выбросах — ровно случай `start_char`, который монотонно растёт
  внутри документа и сбрасывается на его границе.

Единственный код переменной длины во всём формате — `bit-varint(k)`: значение режется на
группы по `k` бит, каждой группе предшествует бит продолжения. Код полный (биективный):
`g` групп кодируют ровно `[base(g), base(g)+2^{gk})`, где `base(g)=Σ_{i<g} 2^{ik}`, поэтому
кодовые пространства разных длин не перекрываются и ни одно значение не тратится зря.

## 3. Текстовый кодек — статический словарь фраз

Это 85 % результата, поэтому подробно.

### 3.1 Атомы

Значение разбивается на **атомы**: максимальный пробег «словных» символов
(ASCII-буквы/цифры и кириллица U+0400–U+04FF) либо максимальный пробег всех остальных
символов (пробелы, знаки препинания, кавычки, тире). Разбиение однозначно и обратимо,
работа идёт прямо на UTF-8 байтах JSON-значения (вместе с escape-последовательностями —
поэтому кодек побайтово точен по построению и не занимается разбором JSON-строк).

Измерено на `full_text`: 16 588 107 слов, 793 686 различных словоформ, 13.52 байта на
слово; 13 751 различный разделитель, из которых один пробел покрывает 76 % вхождений.

### 3.2 Словарь = префиксное дерево над атомами

Узел дерева — последовательность атомов, то есть строка текста. Узлы глубины 1 — сами
атомы. **В таблицу атомов всегда входят все 256 однобайтовых строк и все встреченные в
датасете символы**, поэтому любая последовательность байт кодируема, и escape-механизм
для «незнакомого» текста не нужен вообще: незнакомый атом раскладывается на символы,
незнакомый символ — на байты.

### 3.3 Обучение

1. Считаются частоты атомов; в таблицу попадают атомы с частотой ≥ 3.
2. Дерево инициализируется узлами глубины 1.
3. **Раунд** (16 раундов): обучающий поток разбирается текущим деревом, считается, какой
   атом чаще всего следует за каждым выданным узлом, самые частые продолжения добавляются
   новыми узлами. За раунд фразы удлиняются на один атом. Порог отбора подбирается по
   гистограмме частот так, чтобы попасть в бюджет раунда.
4. Итоговые частоты узлов пересчитываются; фраза, которая не окупает ~5 байт своего места
   в словаре (бездетная, частота ≤ 6), выбрасывается; узлы нумеруются по убыванию частоты.
5. **Уточняющая итерация**: частоты пересчитываются уже оптимальным разбором — тем самым,
   который применит кодер, — после чего нумерация и параметр `k` подбираются заново.

Разбор всегда идёт в границах отдельного значения: фраза не может пересекать границу двух
значений столбца.

Итог на этом датасете: 417 082 атома (из 846 412 различных), **1 322 080 узлов**, в среднем
**14.59 байта текста на один выданный код**.

### 3.4 Кодирование: оптимальный разбор

Жадный «самый длинный подходящий узел» **не оптимален**, когда длины кодов различаются:
длинная редкая фраза может иметь высокий номер (длинный код), а два коротких частых узла —
суммарно более короткий. Поэтому кодер решает задачу кратчайшего пути по решётке разбиений
динамикой с конца:

```
cost[i] = min по всем узлам, покрывающим atoms[i..j)  ( codeBits[узел] + cost[j] )
```

Это стоит ровно столько же обходов дерева, что и жадный разбор, только начиная с каждой
позиции, а декодеру знать об этом ничего не нужно — он просто читает номера узлов.
Замер: жадный разбор 6.40x → оптимальный 6.51x → плюс границы значений и уточняющая
итерация 6.57x.

### 3.5 Код номера узла

Номер узла — его ранг по частоте, ранги пишутся кодом `bit-varint(k)`; частым фразам
достаются короткие коды. Параметр `k` **подбирается кодером** по измеренной таблице частот
(перебор k = 3…26, выбор минимума) и пишется в заголовок; на этом датасете k = 5, что даёт
17.78 бита на код.

### 3.6 Хранение словаря

* **Таблица атомов** — отсортирована лексикографически и сжата префиксным (front) кодированием:
  для каждого атома длина общего префикса с предыдущим + остаток.
* **Таблица узлов** — пара (родитель, атом) на узел. Родитель — это ранг, а ранги
  родителей сильно скошены к нулю (частые фразы наращиваются из частых), поэтому для
  родителя выгоден bit-varint; номер атома распределён почти равномерно, поэтому для него
  выгодна фиксированная ширина. Замер: смешанная схема 8.40 МБ против 8.89 МБ при
  фиксированной ширине для обоих полей и 9.45 МБ при байтовых varint для обоих.
* Родитель может иметь больший номер, чем ребёнок, поэтому развёртывание узлов в строки
  делается отложенно, по стеку — перестановка «ранг → структура» не хранится вообще.

## 4. Соблюдение ограничений задания

| ограничение | как выполнено |
|---|---|
| **Нет готовых кодеков, форматов и библиотек** | только JDK (`java.io`, `java.nio.file`, `java.time.LocalDate`, `java.util.Arrays.sort`, `MessageDigest` для проверки). Битовые потоки, хеш-таблицы, сортировки, словарь — свои. Ни zlib/zstd/lz4, ни Protobuf/AVRO/Parquet |
| **Нет энтропийного кодирования** | нет ни Хаффмана, ни арифметического/дальностного кодирования, ни ANS/rANS, ни адаптивных контекстных моделей. Все коды — статические целочисленные: фиксированная ширина, `bit-varint(k)`, зигзаг, RLE, FOR/PFOR. Длина кода зависит только от **величины** числа, а не от таблицы вероятностей — см. оговорку ниже |
| **Столбцы кодируются независимо** | каждый столбец — отдельный блок, декодируемый без обращения к другим столбцам. В частности `n_sentences` и длина массива `sentences` хранятся как два независимых столбца, хотя и равны друг другу; `sentences[].text` кодируется полностью независимо от `full_text`, хотя и является его подстрокой |
| **Строки кодируются независимо** | декодер значения использует только: само значение, предыдущее значение того же столбца (разности, RLE), внешние данные (шаблон, словари, таблицы кодеков из заголовка). Разностные и RLE-режимы самодостаточны внутри куска из 1024 значений, поток фраз не пересекает границу значения |

### Две оговорки, которые стоит проговорить на защите

1. **Ранжирование по частоте.** Номера узлов словаря назначаются по убыванию частоты, и
   `bit-varint` даёт частым узлам короткие коды. Формально это «использование статистики»,
   но это не энтропийный кодер: код фиксирован, не адаптивен, длина определяется величиной
   номера, а семейство кодов не подгоняется под распределение (подбирается один
   структурный параметр `k`, как основание у любого varint). Это стандартное словарное
   кодирование и сжатие целых, как в обратных индексах и колоночных СУБД.
   Для сравнения: замер показал, что при **фиксированной** ширине кода (чистый LZW-стиль,
   вообще без частот) результат отличается на доли процента — 19.4 бита на код против
   log₂(664 876) = 19.34 — то есть выигрыш даёт словарь фраз, а не ранжирование.
2. **Словарь общий для всех текстовых столбцов** (`full_text`, `sentences[].text`, `title`).
   Он обучен на тексте всего датасета и лежит в заголовке как внешние данные; декодеру
   любого значения не нужны значения другого столбца. Отдельные словари на столбец стоили
   бы примерно вдвое дороже по заголовку при том же результате.

## 7. Обоснование сжатия

### 7.1 Что даёт каждый механизм

| + фразы из 2 атомов (`--rounds=1`) | ≈ 89 300 000 | **5.93x** |
| + фразы до 5 атомов (`--rounds=4`) | ≈ 81 900 000 | **6.47x** |
| + фразы до 17 атомов, 16 раундов, жадный разбор | ≈ 82 800 000 | 6.40x |
| + оптимальный разбор | ≈ 81 400 000 | 6.51x |
| + границы значений и уточняющая итерация | **80 657 358** | **6.57x** |

(размеры промежуточных вариантов пересчитаны из измеренных коэффициентов)

Видно распределение вклада: структура и малокардинальные столбцы дают 1.15x, словарь
уровня слов — основной скачок до 5.33x, фразы добавляют ещё +23 %, оптимальный разбор +2.6 %.

Подбор параметров (все замеры на полном файле):

| параметр | значения | лучший |
|---|---|---|
| порог частоты атома | 2 → 6.47x, **3 → 6.57x**, 8 → 6.35x, 24 → 6.24x, 64 → 6.08x | 3 |
| предел размера словаря | 1 048 576 → 6.29x, **2 097 152 → 6.57x** | 2²¹ |
| отсечение фраз по частоте | 0 → 6.37x, 2 → 6.38x, **6 → 6.40x**, 16 → 6.35x | 6 |
| обучающая выборка | каждый 2-й документ → 6.14x, **каждый → 6.57x** | все |

Обе границы видны явно: при слишком маленьком словаре не хватает длинных фраз, при
слишком большом за них платит заголовок (8.4 МБ — уже 10 % результата).

### 7.2 Насколько это близко к пределу без энтропийного кодирования

Полезный ориентир — **нулевого порядка энтропия того же разбиения на слова**. Замерено
на `full_text`: оптимальный код Хаффмана для потока словоформ занял бы 28.1 МиБ, для
потока разделителей — 3.5 МиБ, итого **31.6 МиБ**. Наш столбец `full_text` — 33 989 977 Б
= **32.4 МиБ**, то есть на 2.6 % больше, чем дал бы Хаффман по словам, — при том, что
энтропийного кодера у нас нет вообще. Словарь фраз забирает то, что Хаффман по словам
взять не может (порядок слов), и этим окупает отсутствие энтропийного кодирования.

### 7.3 Сравнение с эталонными кодеками (весь файл)

| кодек | размер | коэффициент | энтропийное кодирование | междустолбцовая избыточность |
|---|---|---|---|---|
| gzip −6 | 84 708 334 | 6.25x | Хаффман | окно 32 КБ — забирает |
| zstd −3 | 84 326 285 | 6.28x | FSE + Хаффман | забирает |
| gzip −9 | 83 226 599 | 6.36x | Хаффман | забирает |
| **HCF (наш)** | **80 657 358** | **6.57x** | **нет** | **не используется (запрещено)** |
| bzip2 −9 | 63 906 417 | 8.29x | Хаффман по BWT | забирает |
| zstd −19 | 54 561 673 | 9.71x | FSE + Хаффман | забирает |
| xz −6 | 53 200 664 | 9.96x | дальностный кодер | окно 8 МБ — забирает |

Наш формат обходит gzip на обоих уровнях и zstd на быстром уровне, хотя запрещённого
у нас две вещи, которыми все эти кодеки пользуются свободно:

1. **энтропийное кодирование** — обычно даёт 1.3–1.5x сверху;
2. **междустолбцовая избыточность** — `sentences[].text` является точной подстрокой
   `full_text` той же строки. Проверено на всём датасете: во **всех 996 964 предложениях**
   `full_text[start_char:end_char]` посимвольно равно `sentences[].text`. LZ-кодеки с окном
   больше одной строки (у строки средний размер 10 КБ) забирают эту копию целиком, а
   правило 3 запрещает нам это использовать.

Цена второго ограничения измерима точно: столбец `sentences[].text` стоит нам
**34 846 385 байт — 43 % результата**. Если бы обращение к другому столбцу было разрешено,
предложение восстанавливалось бы как `full_text[start_char:end_char]`, то есть **бесплатно**
(оба целочисленных столбца уже есть в файле), и формат дал бы
`80 657 358 − 34 846 385 = 45 810 973` байта, то есть **11.56x** — лучше, чем xz, и
по-прежнему без всякого энтропийного кодирования. Мы этого не делаем: правило 3 явно
запрещает, и столбец кодируется заново с нуля.

Иначе говоря, 6.57x против 9.96x у xz — это не отставание метода, а стоимость двух
ограничений: снимите только правило 3 — и тот же формат даёт 11.56x.

## 8. Как запустить

```bash
# полный цикл: кодирование + декодирование + проверка sha256
./gradlew roundtrip -Pinput=dataset.jsonl
```

```bash
# по шагам
./gradlew installDist
build/install/opus/bin/opus encode dataset.jsonl dataset.hcf
build/install/opus/bin/opus decode dataset.hcf dataset.decoded.jsonl
build/install/opus/bin/opus verify dataset.jsonl dataset.decoded.jsonl
```

```bash
# без Gradle
javac -encoding UTF-8 -d build/classes $(find src/main/java -name '*.java')
java -Xmx8g -cp build/classes com.volhv.Main roundtrip dataset.jsonl out.hcf back.jsonl
```

Параметры словаря (все имеют разумные значения по умолчанию, подобранные замерами):

```
--group=N       строк в группе (4096)
--sample=N      обучать словарь на каждом N-м документе (1)
--min-atom=N    минимальная частота атома для попадания в таблицу (3)
--rounds=N      раундов наращивания фраз (16)
--max-nodes=N   предел размера словаря (2097152)
--min-pair=N    минимальная частота продолжения, чтобы стать фразой (4)
--prune=N       отсечение бездетных фраз по итоговой частоте (6)
```

## 10. Структура кода

```
src/main/java/com/volhv/
  Main.java              CLI: encode / decode / verify / roundtrip, отчёт о размерах
  hcf/
    Bits.java            битовые потоки, bit-varint(k), зигзаг, байтовые varint
    ByteVec, IntVec      растущие буферы без боксинга
    Maps.java            хеш-таблицы: байтовые строки → id, long → int
    Lines.java           потоковое чтение строк без аллокаций
    Template.java        шаблон строки JSONL: вывод, разбор, обратная сборка
    Tokenizer.java       разбиение текста на атомы
    Vocab.java           словарь фраз: матчер, оптимальный разбор, (де)сериализация
    VocabBuilder.java    обучение словаря
    IntCodec.java        самонастраивающийся кодек целых (6 режимов)
    Columns.java         статистика, выбор кодека, кодирование блоков столбцов
    Encoder.java         два прохода по файлу, запись формата
    Decoder.java         чтение формата, побайтовое восстановление JSONL
```
